Security & Encryption Mastery: Protecting Credit Cards from Frontend to Backend

Category: Security Lab Date: 2026-11-22 Agent: security-mentor Status: Published PCI DSS v4.0 + RFC 7516 (JWE)

Your real-world problem: A customer types their credit card number into your Frontend (FE), and right now it gets sent to your Backend (BE) without application-layer protection. Let's fix that — and along the way, learn how Encryption, Decryption, Hashing, TLS, and Secrets Management work using friendly analogies, live browser cryptography, and animated flows!

1. The Friendly Big Picture: From Postcards to Armored Vaults

Think of sending a raw credit card number from your Frontend to your Backend like writing your Visa number on a paper postcard and tossing it into public mail. Anyone along the route — public Wi-Fi routers, proxies, CDN nodes, or log collectors — can read it.

⚠️ Surprising Catch: Why HTTPS (TLS) Alone Isn't Always Enough!
Putting that postcard inside a sealed armored truck (HTTPS / TLS 1.3) stops coffee-shop Wi-Fi hackers! However, the truck usually unloads at your Load Balancer or API Gateway (called TLS Termination). Once unloaded, internal HTTP logs, APM tools (Datadog/Sentry), and your web server memory all see the raw card number in plaintext — pulling your entire backend into strict PCI DSS audit scope.

5 Everyday Analogies (Never Confuse These Again!)

🔤 1. Encoding (Base64)

NOT Security!

Analogy: Pig Latin. It just changes how letters look so systems can carry binary safely over JSON/URLs.

Zero secret key needed — any attacker runs atob() and reads your card in 1 millisecond.

🍓 2. Hashing (SHA-256 / Argon2id)

One-Way Only

Analogy: A Fruit Smoothie. You can blend strawberries into a smoothie, and match a recipe later, but you can never un-blend the smoothie back into whole berries.

Perfect for passwords (with a random Salt), but useless for sending a card number that your payment gateway must charge.

🔑 3. Symmetric (AES-256-GCM)

Fast + Tamper Proof

Analogy: A Shared Safe Key. One secret key both locks and unlocks the box. Modern CPUs run AES blazingly fast.

Catch: If you put that shared key in Frontend JavaScript, anyone opening browser DevTools steals it!

🔓 4. Asymmetric (RSA-OAEP / ECC)

Public Lock, Private Key

Analogy: Open Padlocks + Bank Key. The server hands out unlocked Public Padlocks to every browser. Anyone can snap one shut, but only the server's secret Private Key opens it.

Solves key sharing, though RSA math is slower and limited in payload size.

📦 5. Hybrid JWE (RSA + AES-GCM)

Best App-Layer Lock

Analogy: Padlock Guarding a Disposable Safe Key. Frontend invents a brand-new 1-time AES safe key, locks the credit card inside, and locks that tiny AES key with the server's RSA Public Padlock.

Standardized as JWE (RFC 7516) — fast, safe, and detects even a 1-bit tamper!

🎟️ 6. Hosted Fields + Tokenization

Gold Standard (PCI SAQ A)

Analogy: Valet Parking Ticket. The customer hands their card directly to a certified PCI Vault inside an isolated iframe. Your app only holds a claim ticket (tok_9f3a).

Even if a hacker steals your logs or DB, tok_9f3a cannot be spent elsewhere.

System Design Foundations (Reused & Expanded from Designed to Scale: 07. Security)

🚚 Pillar 1: Data in Transit

TLS 1.3 (HTTPS) uses an asymmetric handshake to verify the server certificate and negotiate ephemeral symmetric session keys in 1 round trip — encrypting all traffic over public networks. Adding JWE adds a second lock inside the HTTP body so proxies can't peek.

🏦 Pillar 2: Data at Rest

Never store raw PAN or CVV in plain DB columns! Production vaults use Envelope Encryption: a fast Data Encryption Key (DEK, AES-256) encrypts each record, while a Master Key (KEK) inside KMS / HSM encrypts the DEK itself.

🗝️ Pillar 3: Secrets & Key Rotation

Never hardcode private keys, DB passwords, or API keys in Frontend code or Git commits. Keep secrets in HashiCorp Vault / AWS KMS, tag public keys with a Key ID (kid), and rotate keys regularly with zero downtime.

4. Solving Your FE → BE Credit Card Problem: Engineering Guide

4.1 Decision Matrix: Pick the Right Architecture

Approach Wi-Fi Sniffer Proxy / Log Leak Tamper Detection XSS Script Immunity PCI DSS 4.0 Scope
❌ Plaintext HTTP Exposed Exposed None None Fails Audit
❌ FE Hardcoded AES Key Broken (Key Public) Fake Security Optional None Fails Audit
⚠️ HTTPS / TLS 1.3 Only Protected Exposed at LB/Logs TLS Record MAC DOM Readable SAQ D (Heavy)
🛡️ Hybrid JWE + TLS 1.3 (FE → BE) Double Locked Opaque JWE AES-GCM AuthTag Needs CSP + SRI SAQ A-EP / D

Rule of Thumb: If you use a Payment Gateway (Stripe, Adyen, Braintree, CyberSource, etc.), choose Option A: Hosted Fields + Tokenization so raw cards never touch your FE DOM or BE. Only build Option B: Hybrid JWE when your backend strictly must receive the raw PAN (e.g., multi-PSP smart routing or an internal PCI-certified vault).

4.2 Strict TypeScript Blueprints (FE + Node.js BE)

🏆 Option A: Hosted Fields + Tokenization (Recommended)

The card input lives inside the PSP's cross-origin iframe. Your Frontend only receives an opaque token, and your Backend only ever types and charges that token. 

// shared/payment-types.ts
export interface PaymentTokenRequest {
  readonly paymentToken: string; // e.g. "tok_9f3a..."
  readonly amountCents: number;
  readonly currency: "USD" | "VND";
  readonly idempotencyKey: string;
}

export interface ChargeResult {
  readonly status: "succeeded" | "requires_action";
  readonly last4: string;
  readonly chargeId: string;
}

// frontend/checkout.ts
export async function submitHostedCheckout(
  pspSdk: { createToken(): Promise<{ readonly tokenId: string }> },
  amountCents: number
): Promise<ChargeResult> {
  const { tokenId } = await pspSdk.createToken();
  const body: PaymentTokenRequest = {
    paymentToken: tokenId,
    amountCents,
    currency: "USD",
    idempotencyKey: crypto.randomUUID(),
  };
  const res = await fetch("/api/v1/charges", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(body),
  });
  if (!res.ok) throw new Error(`Charge failed: ${res.status}`);
  return (await res.json()) as ChargeResult;
}

🛡️ Option B (Part 1): Frontend Hybrid JWE Encrypt

When BE must receive the card: fetch the server's RSA-OAEP-256 public JWK (with kid) and pack card JSON into RFC 7516 JWE using jose (or native Web Crypto). 

// frontend/encrypt-card.ts (uses `jose` + strict TS)
import { CompactEncrypt, importJWK, type JWK } from "jose";

export interface CardInput {
  readonly pan: string;
  readonly expMonth: string;
  readonly expYear: string;
  readonly cvv: string;
}

export interface ServerPublicKey {
  readonly kid: string;
  readonly jwk: JWK;
}

export async function encryptCardToJwe(
  card: CardInput,
  serverKey: ServerPublicKey
): Promise<string> {
  const rsaPublicKey = await importJWK(serverKey.jwk, "RSA-OAEP-256");
  const plaintextBytes = new TextEncoder().encode(JSON.stringify(card));

  return new CompactEncrypt(plaintextBytes)
    .setProtectedHeader({
      alg: "RSA-OAEP-256",
      enc: "A256GCM",
      kid: serverKey.kid,
      typ: "JWE",
    })
    .encrypt(rsaPublicKey);
}

🛡️ Option B (Part 2): Backend JWE Decrypt, Key Rotation & RAM Wipe

The Node.js Backend looks up the private key by kid (from KMS/HSM or rotated keyring), validates the decrypted unknown payload with strict type narrowing, tokenizes at the PSP, and clears plaintext buffers immediately. 

// backend/decrypt-card.ts (Node.js + strict TypeScript)
import { compactDecrypt, type KeyLike } from "jose";

export interface DecryptedCard {
  readonly pan: string;
  readonly expMonth: string;
  readonly expYear: string;
  readonly cvv: string;
}

export interface KeyResolver {
  getPrivateKey(kid: string): Promise<KeyLike>;
}

function assertDecryptedCard(data: unknown): DecryptedCard {
  if (typeof data !== "object" || data === null) {
    throw new Error("Invalid decrypted card envelope");
  }
  const rec = data as Record<string, unknown>;
  if (
    typeof rec.pan !== "string" ||
    typeof rec.expMonth !== "string" ||
    typeof rec.expYear !== "string" ||
    typeof rec.cvv !== "string"
  ) {
    throw new Error("Missing required card fields");
  }
  return { pan: rec.pan, expMonth: rec.expMonth, expYear: rec.expYear, cvv: rec.cvv };
}

export async function handleEncryptedCheckout(
  jweToken: string,
  keys: KeyResolver,
  tokenizeWithPsp: (card: DecryptedCard) => Promise<string>
): Promise<{ readonly pspToken: string; readonly last4: string }> {
  let plaintext: Uint8Array | null = null;
  try {
    const result = await compactDecrypt(jweToken, async (protectedHeader) => {
      if (typeof protectedHeader.kid !== "string") {
        throw new Error("Missing JWE key ID (kid)");
      }
      return keys.getPrivateKey(protectedHeader.kid);
    });
    plaintext = result.plaintext;
    const parsed: unknown = JSON.parse(new TextDecoder().decode(plaintext));
    const card = assertDecryptedCard(parsed);
    const pspToken = await tokenizeWithPsp(card);
    return { pspToken, last4: card.pan.slice(-4) };
  } finally {
    // Wipe sensitive card bytes from memory as soon as PSP call finishes
    if (plaintext !== null) plaintext.fill(0);
  }
}

4.3 What Happens After Decryption? (Envelope Encryption & Secrets Management)

📦 Envelope Encryption (At Rest)

If an authorized vault ever stores sensitive PII or PANs in a database, it avoids sending megabytes of data to a cloud KMS on every read/write:

  1. Generate a fast random DEK (Data Encryption Key) to encrypt the record locally with AES-256-GCM.
  2. Ask AWS KMS / HashiCorp Vault to encrypt just that tiny DEK using the master KEK (Key Encryption Key) — which never leaves the HSM!
  3. Store { encryptedRecord, encryptedDek, kekVersion } together. Rotating the KEK never requires re-encrypting terabytes at once.

🛑 Strict Storage Rules (PCI DSS Req 3)

  • NEVER store CVV/CVC: Prohibited after authorization — not in SQL, Redis, logs, or dead-letter queues.
  • Store Tokens + Masked Display: Save tok_9f3a, brand, and last4 (max first 6 + last 4 digits if masking PAN).
  • Redact Request Logs: Configure API Gateway, Express/Fastify logger (pino.redact), and Sentry beforeSend to strip jweCard, pan, and cvv.

4.4 Top 7 Security Mistakes to Avoid

1. Hardcoding an AES Secret in Frontend JS
Anything shipped to the browser (env vars like VITE_AES_KEY, obfuscated JS) is public. Attackers read it in seconds via DevTools. Only Public Keys belong on the Frontend!
2. Reusing an AES-GCM IV / Nonce
Never use a fixed IV like 0000...! Reusing an IV with the same AES-GCM key breaks confidentiality and lets attackers forge Auth Tags. Always use crypto.getRandomValues(new Uint8Array(12)) per request.
3. Using AES-ECB, Unauthenticated AES-CBC, or RSA1_5
Legacy modes leak patterns or allow Bleichenbacher / padding-oracle attacks. Stick strictly to RSA-OAEP-256 (or ECDH-ES+A256KW) + A256GCM.
4. Ignoring XSS / Magecart Script Skimmers (PCI DSS 4.0)
Even perfect JWE only locks data after JavaScript reads the input. Under PCI DSS 4.0 Req 6.4.3 & 11.6.1, lock payment pages with strict Content-Security-Policy (CSP), Subresource Integrity (SRI) hashes, and script-tamper alerts — or use Hosted Fields iframes!
5. Rolling Your Own Crypto Packing
Don't invent custom string concatenation like iv + ":" + ct without authenticating headers. Use standard JWE (RFC 7516) via battle-tested libraries like jose.
6. Forgetting Key Rotation (kid)
If your single RSA key leaks or expires, rotating without a kid (Key ID) header breaks active checkouts. Serve JWKS with overlapping old/new keys during rotation windows.
7. Logging Request Payloads or Sending Raw Cards to Error Trackers
Even an encrypted JWE or plaintext fallback caught in an unhandled exception handler can leak into APM/Sentry if captured before/after decryption. Redact at middleware level and wipe buffers in finally blocks.
