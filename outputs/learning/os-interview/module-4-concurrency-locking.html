Module 4: Concurrency, Locks, Deadlocks & False Sharing

Interactive Lesson Date: 2026-11-14 Agent: cs-mentor Fresher → Senior

This is the #1 favorite topic in backend interviews: race conditions, Mutex vs. Semaphore vs. Spinlock, Deadlocks, Priority Inversion, Linux Futex, and CPU Cache False Sharing.

1. Daily-Life Analogies: Baristas, Bathroom Keys & Hallway Standoffs

☕ Concurrency vs. Parallelism = 1 vs. 2 Baristas

Concurrency is 1 barista juggling two orders—steaming milk for Alice while Bob's espresso pours (time-slicing). Parallelism is 2 baristas at 2 espresso machines making both drinks simultaneously.

🔑 Mutex vs. Semaphore vs. Spinlock vs. RWLock

Mutex = single restroom key (who locks must unlock). Semaphore = parking lot counter with 5 passes (any car exiting frees a spot). Spinlock = knocking on the bathroom door every 0.1s (burns energy, only smart if they'll exit in 2s!). RWLock = museum room: 50 visitors read quietly together, or 1 janitor closes the room to mop.

🚶 Deadlock vs. Livelock = Narrow Hallway

Deadlock: Alice & Bob freeze face-to-face waiting for the other to step back. Livelock: Both politely step left, then both step right in sync—moving constantly yet making zero progress!

🃏 False Sharing = Two Writers on One Index Card

Alice writes on the left half of a 64-byte index card; Bob writes on the right half. Even though their notes don't overlap, they keep snatching the whole card back and forth across CPU cores!

3. Interview Question Deep-Dive (Fresher → Senior)

Fresher Core OS

Q1. Concurrency vs. Parallelism (on 1 CPU Core vs. Multiple Cores)

🎙️ 30-Second Answer: "Concurrency is about structure—dealing with multiple tasks making progress over overlapping time (even on 1 CPU core via fast context-switching/time-slicing). Parallelism is about execution—literally running multiple instructions at the exact same nanosecond on multiple CPU cores."
Fresher Core OS

Q2. What is a Critical Section & Race Condition? How do you fix it?

🎙️ 30-Second Answer: "A Critical Section is a block of code accessing shared mutable state. A Race Condition happens when two threads enter it concurrently and the final result depends on unpredictable OS thread scheduling (e.g., count++ compiles into 3 CPU steps: Load, Add, Store). We fix it using Mutual Exclusion (Mutex/Lock), Atomic CPU instructions (std::atomic / CAS), or avoiding shared state via message passing."
Mid Core OS

Junior Core OS

Q4. What is Deadlock (4 Coffman Conditions) & how do you prevent it?

🎙️ 30-Second Answer: "Deadlock happens when threads permanently block each other. All 4 Coffman conditions must hold simultaneously: 1) Mutual Exclusion, 2) Hold & Wait, 3) No Preemption, and 4) Circular Wait. Break any single one to prevent deadlock—the most practical fix in real code is breaking Circular Wait via Global Lock Ordering (always lock id_low before id_high)."
// C++/Go style Deadlock-Free Transfer: Always lock lower account ID first!
func Transfer(from, to *Account, amount int) {
    first, second := from, to
    if from.ID > to.ID { first, second = to, from }
    first.mu.Lock(); defer first.mu.Unlock()
    second.mu.Lock(); defer second.mu.Unlock()
    from.Balance -= amount; to.Balance += amount
}
Junior Core OS

Q5. Deadlock vs. Livelock vs. Starvation

🎙️ 30-Second Answer: "In Deadlock, threads are blocked/sleeping at 0% CPU. In Livelock, threads are actively running (100% CPU!) retrying and backing off in lockstep without progressing (fixed with randomized jitter backoff). In Starvation, one thread runs fine while a lower-priority thread is perpetually skipped."
Mid Production

Q6. What is Priority Inversion (and how did NASA fix it on Mars Pathfinder)?

🎙️ 30-Second Answer: "Priority Inversion happens when a Low-priority task holds a mutex needed by a High-priority task, and a Medium-priority task keeps preempting the Low task—starving the High task indirectly! The fix is Priority Inheritance (the Low task temporarily inherits the High task's priority until it unlocks) or Priority Ceiling."
Senior Internals

Q7. What is a Linux Futex (Fast Userspace Mutex)?

🎙️ 30-Second Answer: "A Futex combines a 32-bit user-space integer with a kernel wait queue. On the fast path (uncontended), a thread acquires/releases the lock using a single CPU atomic CAS in user space—zero system calls! Only on contention does the thread invoke futex(FUTEX_WAIT) to sleep in the kernel until the owner calls FUTEX_WAKE."
Senior Hardware-OS

Q8. CPU Cache Lines, MESI & False Sharing

🎙️ 30-Second Answer: "CPUs transfer RAM in 64-byte Cache Lines. If Thread 1 on Core 0 increments counters[0] and Thread 2 on Core 1 increments counters[1], both variables sit on the same 64-byte cache line. The hardware MESI cache coherency protocol constantly invalidates the line between cores, crippling speed by 10×! Fix it by padding/aligning fields to 64 bytes (alignas(64)) or accumulating in thread-local variables."
// C++ Fix for False Sharing: force separate 64-byte cache lines
struct alignas(64) PaddedCounter {
    std::atomic<long> value;
};
