Module 2: Context Switching, Fork/COW, Debuggers & IPC

Interactive Lesson Date: 2026-11-14 Agent: cs-mentor Junior → Senior

How does one CPU juggle 500 programs without mixing up their variables? Why is fork() instant even for a 20 GB database? And how can two isolated processes actually talk—or how does a debugger pause a live app mid-line?

1. Daily-Life Analogies: Surgeons, Photocopiers & Office Intercoms

🩺 Context Switch = A Surgeon Changing Cases

Switching between two threads is like a surgeon putting down a scalpel and picking up a suture in the same operating room. Switching between two processes is scrubbing out, walking to a brand-new operating room, and loading a new patient's chart (new Page Table + cold CPU caches!).

📄 Copy-on-Write = Shared Textbook Pages

When a parent clones itself via fork(), the OS doesn't photocopy a 1,000-page textbook. Parent and Child share the exact same pages with a sticky note saying "Read-Only!" The moment Child grabs a pen to scribble on Page 42, the OS photocopies just Page 42 for Child.

📢 OS IPC = Ways Offices Talk

Pipes = a one-way pneumatic tube. Shared Memory = a shared whiteboard in the hallway (fastest, needs a lock!). Sockets = phone calls that work locally or across the internet. Signals = tapping someone's shoulder for an urgent interruption.

⏸️ Debugger (ptrace) = Movie Director Calling "Cut!"

A debugger asks the OS kernel to freeze the actor (process), swaps one line in the script with a "STOP HERE" sticky note (0xCC / INT 3), inspects every prop in RAM, and whispers "Action!" to resume.

3. Interview Question Deep-Dive (Junior → Senior)

Junior Core OS

Q1. What is a Child Process? How does fork() + exec() create one?

🎙️ 30-Second Answer: "A child process is spawned by a parent via fork() (or clone()). fork() returns 0 inside the child and the child's PID inside the parent. The child inherits a copy of the parent's address space (via Copy-on-Write), open file descriptors, and environment variables—NOT a shared pointer! Usually the child immediately calls execve() to replace its memory image with a new program."
pid_t pid = fork();
if (pid == 0) {
    // Child process: runs a completely different program
    execlp("ls", "ls", "-la", NULL);
} else {
    // Parent process: waits for child
    waitpid(pid, NULL, 0);
}
Mid Core OS

Q2. How does the CPU Context Switch between Processes vs. Threads?

🎙️ 30-Second Answer: "On a context switch, the kernel saves the outgoing task's CPU registers, Program Counter (RIP), and Stack Pointer (RSP) into its PCB/TCB, then loads the incoming task's state. Switching threads in the same process stops there. Switching processes ALSO switches the Page Table base register (CR3 on x86), which invalidates or tags the TLB—making process switches significantly more expensive."
Mid Core OS

Q3. What is Copy-on-Write (COW), and what happens when a child modifies a parent variable?

🎙️ 30-Second Answer: "Copy-on-Write lets fork() skip copying RAM upfront. Both parent and child page tables point to the same physical frames marked Read-Only. If the child only reads, nothing is copied. The instant either process writes, the CPU triggers a protection Page Fault; the kernel copies just that single 4KB page into a new frame, marks it Read-Write, and resumes."
⚠️ Production Trap (Redis BGSAVE): When Redis forks a background child to dump an RDB snapshot, heavy write traffic in the parent triggers thousands of COW page copies—temporarily doubling RAM usage up to 2×!
Senior Architecture

Q4. How is data safety ensured during context switches (1 Core vs. Multi-Core)?

🎙️ 30-Second Answer: "First, each process has isolated page tables, so Process A cannot touch Process B's memory. Inside the kernel during the actual register/queue swap: on a single core, disabling local interrupts makes the switch atomic. On multi-core CPUs, disabling interrupts on Core 0 doesn't stop Core 1—so the kernel protects runqueues with spinlocks, uses atomic CAS instructions, and relies on hardware cache coherency (MESI) + memory barriers."

Senior Internals

Q6. How does a Debugger (gdb) attach to and modify a running process?

🎙️ 30-Second Answer: "Debuggers use the ptrace() system call (with appropriate permissions/CAP_SYS_PTRACE). Calling PTRACE_ATTACH pauses the target via SIGSTOP and makes the debugger its temporary tracing parent. To set a breakpoint on x86, the debugger saves the instruction byte at that address, overwrites it with 0xCC (INT 3 trap), and resumes. When the CPU hits 0xCC, the kernel pauses the target and notifies the debugger, which can read/write registers (PTRACE_GETREGS) or RAM (PTRACE_POKEDATA)!"
Mid Performance

Q7. Direct vs. Indirect Cost of Context Switching

🎙️ 30-Second Answer: "Saving registers takes only ~1–2 microseconds (direct cost). The real killer is the indirect cost: the new process/thread arrives with a cold L1/L2 CPU cache, polluted branch predictor, and (for processes) TLB misses—causing thousands of extra memory stalls over the next few milliseconds."
Senior Production

Q8. Signals & Reentrancy: Why malloc() or printf() inside a signal handler can deadlock!

🎙️ 30-Second Answer: "A signal can interrupt a thread mid-execution—even while that thread is holding malloc's internal heap lock! If your signal handler also calls malloc() or printf(), it tries to acquire the exact same lock held by the paused thread beneath it—causing an instant self-deadlock. Only call async-signal-safe functions (like write()) or just set a volatile sig_atomic_t flag."
