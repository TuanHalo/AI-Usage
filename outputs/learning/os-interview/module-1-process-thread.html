Module 1: Processes, Threads & CPU Scheduling

Interactive Lesson Date: 2026-11-14 Agent: cs-mentor Fresher → Senior

Every OS interview starts here. If you build a crystal-clear mental model of Processes vs. Threads, State Transitions, and How Sleep/Wakeup Works, half of backend concurrency and debugging questions suddenly feel easy.

1. The Daily-Life Story: Welcome to the Restaurant Kitchen 🍳

Before memorizing kernel terms, picture a busy restaurant street. This single metaphor unlocks almost every question in Module 1:

🏢 A Process = An Entire Restaurant Building

Imagine Burger Palace and Sushi House next door. Each has its own kitchen, fridge (Heap), recipe vault (Code), cash register, and locked doors.

If a chef at Burger Palace drops a pot and sets off the fire sprinkler, Sushi House next door keeps cooking untouched! That is process memory isolation.

👨‍🍳 Threads = Chefs Inside the Same Kitchen

Inside Burger Palace, 3 chefs work together. They share the same fridge & stove (Heap, global variables, open files), so passing ingredients is instant!

Each chef still holds their own private knife roll & order ticket (Stack + CPU Registers) so they don't overwrite what step they're on—until two chefs grab the same salt shaker at once (Race Condition!).

🧑‍🤝‍🧑 Thread Pool = A Permanent Crew of 5 Chefs

Imagine hiring a new chef from Craigslist, training them, and firing them for every single burger order. You'd go bankrupt! Instead, you keep 5 permanent chefs waiting by an order ticket board (Task Queue).

📟 Sleep / Wait = Restaurant Buzzer (Not Screaming!)

When your steak takes 10 minutes on the grill, the chef doesn't stand frozen yelling "IS IT DONE? IS IT DONE?" every millisecond. They set a kitchen timer (Wait Queue + Hardware Interrupt) and go prep salad for another table!

3. Interview Question Deep-Dive (Fresher → Senior)

Filter by your target level! Each card gives you a 30-second spoken answer, friendly intuition, code/Linux proof, and the hidden trap interviewers listen for.

Fresher Core OS

Q1. What is a Process vs. a Thread? What are the main differences?

🎙️ 30-Second Interview Answer: "A process is an independent running program with its own isolated virtual memory space and OS resources (like file descriptors). A thread is the smallest unit of CPU execution inside a process. Threads within the same process share the same memory (heap, globals, code) and file descriptors, while each thread keeps its own stack and CPU registers. Because they share memory, threads are faster to create and communicate—but require synchronization to prevent race conditions."
Dimension Process Thread
Analogy Separate restaurant building Chefs inside the same kitchen
Memory Space Isolated (separate page tables) Shared Heap, Code, Global Data
Communication Needs IPC (pipes, sockets, shm) Direct via shared variables (needs locks!)
Crash Blast Radius One process crashing leaves others safe One segfault crashes the whole process
⚠️ Interviewer Trap: Don't say "Processes can never share memory" or "Threads share stacks." Every thread MUST have its own stack (for local variables and function call return addresses), and two processes CAN explicitly share memory using shm/mmap (Module 3).
Junior Core OS

Q2. What data does a Process/Thread need to live? Why is a Thread a "lightweight process"?

🎙️ 30-Second Interview Answer: "The OS tracks a process using a PCB (Process Control Block)—containing its PID, page tables (memory map), open file descriptor table, UID/security permissions, and scheduling state. A thread is tracked with a TCB (Thread Control Block), which only needs a Thread ID, CPU registers (including Program Counter), and its own Stack pointer. It's called a lightweight process because creating or switching threads reuses the parent process's existing memory map and file table—and on Linux, both are actually represented by the same task_struct created via clone() with different sharing flags!"
🏠 Daily-Life Check: Opening a brand-new restaurant requires city permits, a lease, kitchen plumbing, and a fridge (PCB). Adding one more chef to an existing restaurant only needs an apron, a knife roll, and a notepad (TCB).
Junior Core OS

Q3. How many states does a Process have, and how does it transition between them?

🎙️ 30-Second Interview Answer: "The classic 5-state model is New → Ready → Running ↔ Waiting (Blocked) → Terminated (plus Suspended/Swapped states in 7-state models, and Linux's Zombie state). A key point: a Waiting process never jumps directly to Running—when I/O finishes, it moves to Ready and waits for the scheduler to pick it."

👆 Refer to Archify Flow 1 above to watch every arrow animate! Remember the critical interview distinction:

  • Running → Ready: Preempted (time quantum ran out, or higher-priority task arrived). Still wants CPU!
  • Running → Waiting: Voluntary block (read() from disk, sleep(), waiting on a mutex). Gives up CPU voluntarily!
Junior Production

Q4. What are Zombie & Orphan Processes? Why do Zombies matter in production?

🎙️ 30-Second Interview Answer: "A Zombie process has already finished executing, freed its memory and open files, but still sits in the kernel process table because its parent hasn't called wait() to read its exit code. An Orphan process is still running after its parent died—the OS immediately reparents it to init (PID 1), which reaps it when it finishes. Zombies are dangerous in production because while they consume 0 RAM, they leak PIDs—eventually exhausting pid_max so no new processes can start." 
// C: Classic Zombie vs Reaping
pid_t pid = fork();
if (pid == 0) {
    exit(42); // Child finishes immediately
} else {
    sleep(30); // Parent is busy and hasn't called wait() -> Child is a ZOMBIE (stat 'Z')!
    waitpid(pid, NULL, 0); // Now child's PID slot is freed
}
⚠️ Senior Follow-Up (Containers!): Why do Docker containers sometimes accumulate zombies? Because if your container runs python app.py as PID 1, Python doesn't automatically call wait() on orphaned grandchildren! That's why flags like docker run --init (using tini) exist.
Mid Core OS

Q5. Multi-Process vs. Multi-Thread: When should you choose which?

🎙️ 30-Second Interview Answer: "Choose Multi-Process when you need fault/security isolation (like browser tabs in Chrome or running untrusted plugins) or when bypassing a runtime lock like Python's GIL for CPU-bound work. Choose Multi-Thread when tasks share large in-memory state frequently, need cheap creation/context switches, and can tolerate shared-memory synchronization."
⚠️ Python / Node.js Interview Trap: In CPython, multiple threads CANNOT execute Python bytecode simultaneously across multiple CPU cores due to the GIL (Global Interpreter Lock). So in Python: I/O-bound → Threads or Asyncio; CPU-bound → Multiprocessing!
Junior Core OS

Q6. Explain CPU Scheduling Algorithms (FCFS, SJF, Round Robin, MLFQ).

🎙️ 30-Second Interview Answer: "Schedulers balance throughput/turnaround time against responsiveness/fairness. FCFS is simple but suffers from the convoy effect (one huge job blocks tiny ones). SJF minimizes average wait time mathematically, but we can't predict future burst lengths and long jobs can starve. Round Robin gives each task a small time quantum so UI/servers stay responsive. Real OSes like Linux (CFS/EEVDF) and Windows use MLFQ-style priority/fairness queues that boost interactive I/O tasks and prevent starvation."
Mid Core OS

Q7. When a thread sleeps or waits for I/O, how does the CPU detect it's ready to run again?

🎙️ 30-Second Interview Answer: "The CPU does NOT poll or check sleeping threads in a loop! When a thread calls sleep() or blocking I/O, the kernel moves its TCB off the Ready Queue onto a Wait Queue (e.g., timer wheel or disk wait queue) and immediately schedules another thread. Later, a hardware timer interrupt or device IRQ (from disk/NIC) fires, and the kernel's Interrupt Service Routine moves the thread back into the Ready Queue."

👆 Check Archify Flow 2 above for the exact step-by-step sequence! Also remember: sleep(50ms) means at least 50ms, because after waking into the Ready Queue, the thread still waits for the scheduler to assign it a CPU core.

Mid Core OS

Q8. What is a Thread Pool, why use it, and how do you build one?

🎙️ 30-Second Interview Answer: "A thread pool pre-allocates a fixed number of reusable worker threads pulling jobs from a thread-safe bounded task queue. It avoids the latency of repeatedly creating/destroying OS threads, limits total memory used by thread stacks, and prevents CPU thrashing from excessive context switching."
Python (Custom Worker Pool Pattern): 
import queue, threading

tasks = queue.Queue(maxsize=100) # Bounded = backpressure!

def worker():
    while True:
        fn = tasks.get()
        if fn is None: break     # Poison pill shutdown
        try: fn()
        finally: tasks.task_done()

threads = [threading.Thread(target=worker) for _ in range(4)]
for t in threads: t.start()
Go (Idiomatic Worker Pool): 
jobs := make(chan func(), 100)
var wg sync.WaitGroup

for w := 0; w < 4; w++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for job := range jobs { job() }
    }()
}
⚠️ Senior Sizing Question: How big should the pool be?
• CPU-bound work: ~CPU_cores (or cores + 1) — extra threads only add context-switch overhead.
• I/O-bound work: larger, or better yet use non-blocking async I/O (epoll / Go netpoller)! And always bound the queue for backpressure so traffic spikes don't cause Out-of-Memory crashes.
Mid Production

Q9. Kernel Threads (1:1) vs. User-Space Green Threads / Goroutines (M:N)

🎙️ 30-Second Interview Answer: "OS/Kernel threads (1:1, like pthreads or Java platform threads) are scheduled by the kernel, reserve ~1–8 MB virtual stack each, and require expensive kernel syscalls to switch. M:N user-space threads (like Go goroutines or Java virtual threads) multiplex thousands of tiny ~2 KB tasks onto a small pool of OS threads in user space—making creation and switching ~10–50× cheaper."
Senior Production

Q10. Starvation, Priority Aging & Why Linux Load Average Can Be 50 at 10% CPU!

🎙️ 30-Second Interview Answer: "Starvation happens when low-priority tasks never get CPU time because high-priority tasks keep arriving—solved by Aging (gradually boosting priority the longer a task waits). For production debugging: Linux Load Average counts processes in BOTH Running/Runnable (R) AND Uninterruptible Sleep (D) (waiting on disk/NFS). So a Load Average of 50 with 10% CPU usually means disk or network storage I/O saturation, not CPU exhaustion!"
🔥 Senior Diagnostic Checklist: Check vmstat 1 or top: look at wa (% iowait) and procs r (runnable queue) vs b (blocked in uninterruptible sleep). High r > cores = CPU saturation; high b / wa = slow disk/storage!
